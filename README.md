# RohBar — Межгородские грузоперевозки | Боркашонии байнишаҳрӣ

**RohBar** — цифровая платформа для организации межгородских автомобильных грузоперевозок в России с полной локализацией **RU/TG**.

---

# Русский

## Назначение проекта

RohBar объединяет заказчиков, перевозчиков и водителей в единой системе для организации перевозки: от создания заявки и поиска подходящего транспорта до согласования условий, изменения статусов, контроля выполнения и хранения истории заказов.

Проект ориентирован на российский рынок и предназначен для цифровизации межгородских грузоперевозок.

## Возможности платформы

### Заказчик

- регистрация и профиль;
- создание заявки на перевозку;
- указание пунктов погрузки и выгрузки;
- параметры и характеристики груза;
- дата и условия перевозки;
- поиск перевозчиков;
- просмотр предложений;
- согласование условий;
- управление активными и завершёнными заказами;
- просмотр статуса перевозки;
- история заказов.

### Перевозчик

- регистрация и профиль;
- управление автопарком;
- добавление транспорта и его характеристик;
- просмотр и поиск заявок;
- фильтрация по маршрутам и параметрам;
- отклик на заявки;
- управление принятыми перевозками;
- изменение статусов;
- история выполненных перевозок.

### Платформа

- единая система пользователей и ролей;
- управление заявками и заказами;
- маршруты и географические данные;
- уведомления;
- журнал событий;
- административное управление;
- аналитика и статистика;
- локализация RU/TG.

## Направления перевозок

Основной профиль RohBar — **межгородские автомобильные грузоперевозки по России**.

Поддерживаемые сценарии:

- город → город;
- регион → регион;
- склад → склад;
- производство → склад;
- склад → торговая точка;
- прямые междугородние перевозки;
- поиск обратной загрузки для транспорта.

В дальнейшем география и набор направлений могут быть расширены.

## Роли пользователей

| Роль | Назначение |
|---|---|
| **Заказчик** | Создаёт заявки и организует перевозку |
| **Перевозчик** | Находит заявки и выполняет перевозки |
| **Водитель** | Работает с назначенной перевозкой |
| **Администратор** | Управляет пользователями, заявками и системой |

Доступ к данным и операциям определяется ролевой моделью и серверными правилами авторизации.

## Основные функции

### Заявки

Заявка содержит маршрут, груз, требования к транспорту, дату перевозки и дополнительные условия.

### Поиск и подбор

Поиск выполняется по городам отправления и назначения, дате, типу транспорта, типу кузова, характеристикам груза и другим параметрам.

### Жизненный цикл заказа

Базовая модель:

`Создана → На рассмотрении → Принята → В пути → Доставлена → Завершена`

Фактический набор статусов и допустимые переходы определяются бизнес-логикой системы.

### Профили и транспорт

Перевозчик управляет профилем и автопарком. Для транспорта хранятся необходимые характеристики, используемые при подборе заявок.

### Уведомления

Пользователь получает уведомления о новых предложениях, изменениях заказа, назначении перевозки и изменении её статуса.

## Локализация RU/TG

RohBar является двуязычной платформой:

- **RU — русский**;
- **TG — тоҷикӣ / таджикский**.

Локализация охватывает интерфейс, навигацию, формы, статусы, системные сообщения, ошибки, уведомления, справочники и административную часть.

Русский язык ориентирован на основной рынок России, таджикский — на таджикоязычных пользователей платформы.

## Техническая архитектура

Проект строится как модульная клиент-серверная система с разделением frontend, backend, базы данных и внешних интеграций.

```text
┌─────────────────────────────┐
│       Web / Mobile UI       │
│       RU / TG interface     │
└──────────────┬──────────────┘
               │ HTTPS / API
               ▼
┌─────────────────────────────┐
│         Backend API         │
│ auth · roles · business     │
│ requests · orders · fleet   │
└───────┬──────────┬──────────┘
        │          │
        ▼          ▼
┌──────────────┐ ┌────────────────┐
│   Database   │ │ External APIs  │
│ users        │ │ maps / geo     │
│ requests     │ │ notifications  │
│ orders       │ │ integrations   │
│ vehicles     │ └────────────────┘
└──────────────┘
```

Архитектурные принципы:

- API-first;
- разделение ответственности компонентов;
- RBAC и серверная авторизация;
- серверная валидация;
- централизованная бизнес-логика;
- безопасная обработка пользовательских данных;
- журналирование важных операций;
- готовность к горизонтальному масштабированию;
- возможность подключения картографических и других внешних API.

## Требования

Для разработки и запуска потребуются:

Точные версии зависимостей должны фиксироваться непосредственно в конфигурационных файлах проекта после реализации соответствующих компонентов.

Раванди кор аз эҷоди дархост ва ҷустуҷӯи нақлиёт то мувофиқаи шартҳо, тағйири ҳолат, назорат ва нигоҳдории таърихи фармоишҳоро дар бар мегирад.

## Telegram: production setup

Mini App отправляет исходный `Telegram.WebApp.initData` в `POST /api/v1/auth/telegram`
один раз за загрузку приложения. Backend проверяет HMAC и `auth_date`, создаёт обычную
HttpOnly-сессию и возвращает роль из БД. Вход с публичных страниц ведёт перевозчика в
`/fleet`, водителя в `/driver`, заказчика и администратора в `/dashboard`.
`initDataUnsafe` не используется для авторизации. Старые предсказуемые пароли Telegram
заменяются случайным материалом при успешной проверке Telegram-входа; роль, профиль
и пользовательские пароли сохраняются. Для ещё не вошедших старых аккаунтов эта
замена произойдёт при следующем Telegram-входе.

Привязка существующего аккаунта доступна в **Настройки → Telegram**: получить код,
затем отправить `/link 123456` в личном чате бота (поддерживается `/link@имя_бота`).
Код — 6 цифр, включая ведущие нули, действует 10 минут. Регенерация отменяет старый;
повторная доставка уже выполненной команды возвращает успех без повторной привязки.
Код показывается один раз, хранится только в памяти страницы, ответ имеет `Cache-Control: no-store`.
Не передавайте его другим людям: он разрешает вход в ваш аккаунт.

Миграция `0004_telegram_account_linking.sql` добавляет HMAC-SHA256 digest кодов,
признаки происхождения аккаунта/доступности пароля и версию сессии. HMAC использует
существующий `TELEGRAM_BOT_TOKEN` с отдельным префиксом назначения; смена token
делает выданные коды недействительными. Новые секреты не нужны. Redis обязателен:
лимиты 3 выдачи на аккаунт и 5 попыток на Telegram sender за 10 минут, дополнительно
по 100 глобальных выдач/попыток за 10 минут. Ошибки/таймаут Redis запрещают операцию.
Digest хранится до суток после expiry для предотвращения немедленного повторного
использования числа; очистка выполняется при выдаче следующего кода.

Привязка, отвязка и создание/поиск пользователя при Telegram-входе сериализованы
короткой транзакцией PostgreSQL с advisory lock. Роль, профиль и данные целевого
аккаунта сохраняются. Удаляется только созданный новой версией нетронутый Telegram
placeholder без каких-либо FK-ссылок, включая каскадные; изменения профиля навсегда
снимают признак пустого аккаунта. Для старых placeholder происхождение не доказано:
автоматическая привязка к другому аккаунту отклоняется без удаления/переноса данных.
Это требует индивидуального разрешения конфликта, а не автоматического слияния.
Исторические адреса `telegram-…@rohbar.local` не считаются альтернативным входом.

API (серверная cookie-сессия): `GET /api/v1/profile/telegram`,
`POST /api/v1/profile/telegram/link-code`, `POST /api/v1/profile/telegram/unlink`.
Отвязка требует доступного входа по нормальной почте и паролю; единственный способ
входа удалить нельзя. Она инвалидирует коды и все прежние сессии, включая созданные
до миграции; инициирующий браузер получает новую сессию. После привязки следующий
Telegram-вход открывает целевой аккаунт. Для rollback backend сохраняйте миграцию:
старая версия не понимает новые значения Redis-сессий и потребует повторного входа.

Оператору после зелёного CI и отдельного штатного выпуска backend/web:

1. Через защищённый процесс управления конфигурацией задать `TELEGRAM_BOT_TOKEN`
   от BotFather и случайный `TELEGRAM_WEBHOOK_SECRET` (1–256 символов `A-Z a-z 0-9 _ -`).
   Backend и setup должны получать одинаковые значения. `FRONTEND_ORIGIN` должен быть
   `https://rohbar.vosiev.com`; HTTPS endpoint `https://rohbar-api.vosiev.com/api/v1/telegram/webhook` должен быть
   доступен Telegram. Значения секретов не передавать аргументами CLI и не публиковать.
2. Проверить конфигурацию без сетевых вызовов:
   `python3 scripts/setup-telegram.py --check-only`.
3. Отдельно выполнить активацию: `python3 scripts/setup-telegram.py`.
   Скрипт читает `infra/.env` без изменений и без исполнения shell-кода; переменные
   процесса имеют приоритет. Для другого файла есть `--env-file /path/to/env`.
   Требуется только Python 3 со стандартной библиотекой, доступ к `api.telegram.org`
   по HTTPS и доверенные системные CA; HTTP proxy из окружения не используется.
4. Скрипт вызывает `getMe`, `setWebhook` с `secret_token`, `setChatMenuButton`
   с HTTPS Web App и `setMyCommands` (`start`, `link`, `help`), затем сверяет webhook, меню и команды.
   После выпуска привязки повторите setup для добавления `/link` в меню команд.
   Повторный запуск безопасно устанавливает ту же конфигурацию и не удаляет ожидающие
   обновления. При частичной ошибке исправить причину и повторить запуск.
5. В личном чате отправить `/start` и `/help`, открыть кнопку RohBar и проверить
   серверную сессию и посадочную страницу роли; повторить с языком Telegram TG.
   Проверить отказ webhook без `X-Telegram-Bot-Api-Secret-Token` или с неверным значением.
   `getWebhookInfo` не возвращает секрет, поэтому проверка доставки обязательна.
   Кнопки Web App отправляются только в личные чаты. Ошибки `sendMessage` видны в
   backend-логах без token и возвращают HTTP 502 для повторной доставки Telegram;
   при неопределённом исходе сетевого запроса возможен повтор ответа бота.

Проверки скрипта без Telegram/production env:
`python3 -B -m unittest discover -s scripts -p 'test_*.py'`.
Проверки дедупликации frontend-входа после установки зависимостей web:
`node --test scripts/test-telegram-runtime.cjs scripts/test-telegram-link.cjs`.
Интеграционные Rust-тесты используют `ROHBAR_TEST_DATABASE_URL`/`ROHBAR_TEST_REDIS_URL`
(или CI `DATABASE_URL`/`REDIS_URL`), только с изолированными тестовыми хранилищами.

API сверены 2026-09-13 через Context7 и официальные страницы:
[Mini Apps](https://core.telegram.org/bots/webapps) (`telegram-web-app.js?63`, загрузка
до гидратации, raw initData) и [Bot API](https://core.telegram.org/bots/api)
(`secret_token`, HTTPS `WebAppInfo`). Активация не выполняется при сборке или тестах.
